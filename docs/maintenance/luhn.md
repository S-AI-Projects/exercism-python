## 1. Exercise-Specific File-Role Map

The `luhn` practice exercise contains several files with distinct roles across the learner lifecycle, local testing, and automated test evaluation:

| Relative Path | Role Key | Purpose & Contract |
| :--- | :--- | :--- |
| `luhn.py` | `solution` | **Learner Solution Stub.** Initial unsolved code provided to learners defining the class `Luhn` with stubbed methods `__init__(self, card_num)` and `valid(self)`. Must remain strictly unsolved in the repository. |
| `luhn_test.py` | `test` | **Test Suite.** Test cases executed by pytest to validate a student's solution or the track reference implementation. |

| `.docs/instructions.md`| — | **Problem Description.** Human-readable instructions explaining the Luhn formula and verification rules. |

## 2. Metadata-Based Test Runner Discovery Mechanism

Exercism test runners (both in continuous integration and on the Exercism online platform) **do not** use ad-hoc file searches (e.g. searching for `*test*.py` or `*solution*.py`). Instead, they strictly parse `.meta/config.json` to resolve files by their explicit roles:

```json
"files": {
  "solution": [
    "luhn.py"
  ],
  "test": [
    "luhn_test.py"
  ],
  "example": [
    ".meta/example.py"
  ]
}
```

### Discovery & Execution Workflow:
1. **Locating the Test Suite:** The runner reads `config_data["files"]["test"][0]`, resolving `exercises/practice/luhn/luhn_test.py`.
2. **Locating the Reference Solution:** To verify that the exercise suite is healthy, the runner reads `config_data["files"]["example"][0]`, resolving `exercises/practice/luhn/.meta/example.py`.
3. **Scratch Environment Substitution:** The runner copies the exercise directory to an isolated temporary scratch environment, copies `.meta/example.py` onto `luhn.py` (the target declared in `files["solution"]`), and invokes:
   ```bash
   python3 -m pytest -q
   ```
4. **Sandboxing & Boundary Enforcement:** All declared paths must be relative to `exercises/practice/luhn`. Path traversal components (`..`) or absolute paths are strictly rejected to ensure code execution cannot escape the exercise workspace.

## 3. Distinction Between Generated Artifacts & Maintained Sources

Maintaining this exercise requires clearly distinguishing between auto-generated files and hand-maintained files:

### Generated Artifacts
- **`.meta/tests.toml`**: Auto-generated from the central `problem-specifications` repository (`exercises/luhn/canonical-data.json`) via `configlet sync --tests --exercise luhn`. Manual edits are overwritten during synchronization unless stored under a `comment` key.
- **Canonical Tests in `luhn_test.py` (Lines 14–81)**: The 22 canonical test cases corresponding to canonical data UUIDs. When problem specifications update, these tests are regenerated by the track generator (`./bin/generate_tests.py -e luhn`).

### Hand-Maintained Sources
- **`.meta/config.json`**: Track-maintained file specifying contributors, authors, blurb, source, and exact relative file mappings.
- **`.meta/example.py`**: Python reference implementation written and maintained by track contributors.
- **Track-Specific Tests in `luhn_test.py` (Lines 83–90)**: Custom test cases added specifically for the Python track (e.g. `test_is_valid_can_be_called_repeatedly` to detect state mutations between method calls).
- **`luhn.py`**: Initial stub file provided to learners.
